# 10: Content translations & SEO language wiring

**What to build:** The Author maintains independent translation versions for Articles and Posts: add, edit, or delete a version per Locale, with its own title, summary, and body, and set which version is the work's default. A Reader requesting a Locale that has no version of a work sees the default version with a clear "no version in this language" notice — the URL keeps its prefix. The switcher marks which Locales actually exist for the current work. The Feed shows only Posts with a version in the current Locale. Category and Tag display names render per Locale. Language-interlink declarations list only real versions, and fallback pages carry noindex.

**Blocked by:** 02 — Locale routing & site chrome; 05 — First published Article; 07 — Public article reading; 08 — Post feed

**Status:** ready-for-agent

- [x] The translation panel adds, edits, and deletes each Locale version independently for Articles and Posts; deleting one version leaves every other version intact.
- [x] `defaultLocale` is editable and decides which version Content Fallback displays.
- [x] A work requested in a Locale without a version shows the default version's content plus the "no version in this language" notice; the URL prefix stays as requested; the page is noindex.
- [x] The language switcher on a work's page indicates which Locales actually have a version, and switching keeps the Reader on that work.
- [x] The Feed in a given Locale shows only Posts that have a version in that Locale.
- [x] Category and Tag names display in the current Locale.
- [x] Language-interlink and canonical declarations reference only Locales with real versions.

## Comments

Translations became first-class on both sides without a migration, a second Locale list or a second fallback path: `article_translation` / `post_translation` already carry everything needed, so Locale Coverage is read off those rows and nothing is stored.

- **Coverage and fallback are now pure functions** — `src/domain/translation-coverage.ts`: `localeCoverage(translations)` (every Site Locale with `hasVersion`, derived at read time), `coveredLocales(translations)` (only the Locales a declaration may name) and `selectTranslation(translations, requested, defaultLocale)` → `{ translation, fellBack }` (the Reader's own version, else the work's `defaultLocale`, else whatever exists; `null` only for a work with no version). `findReadableArticle` now delegates the choice to it instead of repeating the three `find` calls, so the fallback rule has one definition and one set of dense unit tests. The `locale` parameter is a plain string in the selector precisely so the "defaultLocale before any other version" ordering is testable on a site with more than two Locales — with `siteConfig.locales = ["zh","en"]` and the default-Locale guard, the two-Locale case cannot distinguish the rule from "take the only other version".
- **Language declarations are derived, not assembled per page** — `src/domain/article-language.ts`: `articleLanguageLinks({ slug, shownLocale, translations, headers })` → `{ canonical, versions, alternates }`. `canonical` is the URL of the version the page really shows (so a Content Fallback page canonicalises to the default Locale's URL); `versions` is every Site Locale with its coverage and URL (what the switcher lists); `alternates` keeps only `hasVersion` entries (what the head may declare). Every URL goes through `requestUrl` (request host + `x-forwarded-proto`), never a configured domain; with an unusable Host it degrades to the path, which is what the request actually gave. `alternateLanguageMap(links)` is the one adapter to Next's `alternates.languages` shape.
- **The work switcher is page-scoped, and that is a deliberate decision.** The header `LocaleSwitcher` lives in `[locale]/layout.tsx` and a server layout cannot see the page's Article, so a coverage-aware header switcher is not possible without a second round trip or a client-only marker (which would not be in the served HTML, where the claim has to be readable). Ticket 07's page therefore gained `src/components/article-language.tsx` → `ArticleLanguageVersions`: a `<nav aria-label>` over every Site Locale, each an `<a hrefLang lang>` to the same Slug under that prefix (`aria-current="page"` on the Locale of the URL, `data-version="own|fallback"`), and a Locale without a version carries a visible `.article-locale-note` ("暂无此语言版本") referenced by `aria-describedby`. Nothing 404s: a Locale without a version lands on the Content Fallback page, so the switcher never offers a dead click, and it never claims a version the work does not have. The header switcher keeps its job (prefix swap on every page) and is untouched.
- **The fallback notice** stays exactly one `<p class="reader-notice" role="note">`, now rendered by `FallbackNotice` so its wording and escaping are asserted from markup; the page keeps the requested prefix and stays `noindex` through ticket 05's `indexable` boolean (no re-derivation).
- **Posts gained the two operations Articles already had**: `removePostTranslation` (same refusals, same order: `default-locale`, then `last-translation`; the row only — images, Tags and the work survive) and `setPostDefaultLocale` (refuses a Locale the Post has no version in). `DELETE /api/admin/posts/<id>/translations/<locale>` is the new endpoint, and `PATCH /api/admin/posts/<id>` now accepts `defaultLocale` alongside `tagIds` (one service call per field, tags first, so neither change can undo the other; a body with neither is still `400 invalid-tag-ids`).
- **Admin panels**: the Article editor's Locale row gained a two-step "delete this Locale version" control that is a disabled, visibly explained state when the Locale is the work's default or the last remaining version (the same two rules, in the same order, as the service — no silent failure), and the defaultLocale select now carries the "this is what a fallback shows" hint. The Post composer gained the same removal control plus a defaultLocale select. Deleting a version also clears that Locale's IndexedDB queue, because the bytes typed into a version that no longer exists are not owed to anything; the panel then opens the default version and re-creates the per-Locale sync session.
- **Category and Tag display names**: ticket 07's reading service already used `pickLocalised` everywhere; the one gap was the Article page itself (`names[locale] ?? slug`, which showed a raw slug to a Reader in a Locale the Category/Tag has no name in). It now uses `pickLocalised` like every other public surface, and `services/reading` has a test pinning the rule with latin slugs so a slug-vs-name mistake is unmistakable.
- **The Feed stays locale-strict** — ticket 08's two tests already asserted it (`is locale-strict…`, `never falls back to the default Locale, unlike an Article page`); this ticket adds `drops a Post from a Feed once that Locale's version is removed`, which ties the rule to the new delete path. Content Fallback remains absent from the Feed; `src/app/[locale]/feed/page.tsx` was not touched.
- **Sitemap** needed no change: `listIndexableArticlePaths` already emits one URL per *existing* version, and a Post has no URL at all. Verified live (one `<loc>` for a one-version Article, no feed or fallback entries).
