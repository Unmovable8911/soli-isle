# 06: Article editing resilience

**What to build:** The Author keeps writing while offline; local edits queue and sync automatically when the network returns. If the server copy changed while the Author was away, the Author is told explicitly — nothing is silently overwritten — and can either discard the local changes or save the local version as a new draft.

**Blocked by:** 05 — First published Article

**Status:** ready-for-human

- [x] Losing the network mid-edit does not block writing; on reconnect the local copy syncs to the server without further action.
- [x] When the server copy has changed since the local copy's base version, the editor blocks the overwrite and offers two explicit choices: discard local changes, or save the local version as a new draft. Silent overwrite never happens.
- [x] Closing the browser with unsynced local changes and reopening it recovers those changes.

## Comments

Local-first editing on top of 05's autosave: every keystroke lands in IndexedDB before anything touches the network, the throttle only governs the server round trip, and the queue is durable across reloads. Optimistic concurrency lives at the service seam; the browser only renders the outcome.

- **Schema (migration `0004_dark_speedball`, additive).** `article_translation.version INTEGER NOT NULL DEFAULT 1` — a monotonic per-translation counter, bumped by every save. `createArticleDraft`/`addArticleTranslation`/`restoreRevision` start a row at 1; `restoreRevision` bumps an existing row so an editor still holding the pre-restore version cannot win. Rows written before this migration read back as version 1. The harness schema test now expects the extra column (`PRAGMA table_info` order puts it last).
- **Conflict protocol.** `PUT /api/admin/articles/<id>/translations/<locale>` requires `baseVersion` (a positive integer; anything else is `400 invalid-base-version`). The service compares it with the stored `version` before writing: a mismatch returns `{ ok: false, reason: "stale-content", current: <ArticleTranslationView> }`, the adapter answers **409** with `{ error: "stale-content", current: {...} }` (`no-store`), and nothing is written — the row keeps its title, body and version. A save with the matching version answers 200 and returns the article with `version` incremented. 05's endpoints keep their shapes; every existing service test call site grew a `baseVersion`.
- **Pure reconciliation** — `src/domain/article-sync.ts`, `reconcileArticleEdit(local, server)` → `"in-sync" | "push" | "conflict"`, dense tests in `article-sync.test.ts` (12 cases). Content is compared literally for title/summary and structurally for `bodyJson` (a re-serialised document is the same content); equal content is `in-sync` at any version, a differing body at a different version is `conflict` — including a base version *ahead* of the server, so a rollback cannot be overwritten either.
- **Sync engine** — `src/components/admin/article-sync-engine.ts` (`createArticleSyncEngine`, 13 tests) owns one Locale's queue: `edit` persists then schedules a throttled flush; `flushNow` asks the pure function first and only then calls the transport; a successful ack rebinds a queued edit to the new version instead of dropping it; a `stale` ack or a server-side refusal parks the engine in `conflict` and refuses to send anything else. `offline` keeps the bytes and retries with doubling backoff (2 s → 30 s, `articleConfig.syncRetryBaseMs/MaxMs`), `online` flushes immediately, and no failure path ever clears the store. Statuses: `idle | local | syncing | saved | offline | conflict`.
- **Store interface** — `src/components/admin/article-local-store.ts` is now `ArticleDraftStore` (`save`/`load`/`clear`) with an IndexedDB implementation, a shared memory fallback for tabs without IndexedDB, and `readDraftRecord` (tested) which restores a pre-06 draft with `baseVersion: 0` — an unknown base deliberately becomes a conflict instead of a guessed push.
- **Transport** — `src/components/admin/article-sync-transport.ts` maps the endpoint to `saved | stale | unavailable` (tested with real `Response` objects); anything it cannot parse is `unavailable`, so an unanswered save stays queued rather than being reported as landed.
- **Recovery on open.** Opening (or switching to) a Locale loads the queued draft, restores it into the title, summary and editor, shows `admin.articles.sync.recovered` and immediately retries the sync — the server copy is never presented as if it were current. If the restored bytes conflict, the dialog opens instead of syncing.
- **Conflict dialog.** Two explicit choices plus a non-destructive dismiss: *discard local changes* (re-reads the article, adopts the server copy, clears the queue), *save the local version as a new draft* (creates a new Article from the queued bytes via `POST /api/admin/articles`, clears this Article's queue only after the 201, then opens the new draft), and *keep editing* (dialog closes, bytes stay queued). No auto-merge, no last-write-wins, no silent overwrite anywhere.
- **Typing into a Locale that has no version yet** still persists locally (`baseVersion: 0`); creating the version pushes those bytes into the freshly created row instead of blanking the editor, so that flow cannot lose work either.
- **Unchanged from 05:** autosave writes no Revision snapshot (`saveArticleTranslation` still touches only the translation row); the editor's explicit `POST /revisions` after a successful sync remains, and the service still throttles it to one automatic snapshot per window. `admin.articles.sync.*` was appended to `zh` and `en` with identical structure.

Validation: `npx tsc --noEmit` clean; `npm run lint` 0 errors (the one pre-existing `eslint.config.mjs` warning); `npm test` 37 files / **331 tests** green (43 new: 12 domain, 7 service, 3 HTTP, 6 store, 13 engine, 4 transport, minus the ones rewritten in 05's files); `npm run build` succeeds. Live `next start` on port 3106 (fresh file DB, migrations incl. 0004 applied): login 303 → create draft 201 (`version: 1`) → `PUT baseVersion: 1` 200 with `version: 2` → repeat with the stale `baseVersion: 1` → **409** `{"error":"stale-content","current":{…,"title":"Server copy","version":2}}` with the row unchanged in SQLite → `PUT` without `baseVersion` → 400 `invalid-base-version` → editor page 200 with the new `admin.articles.sync.*` strings; `article_revision` stayed empty throughout.

Accepted scope notes: IndexedDB itself is not tested (the store is behind an interface with a memory implementation, per the spec's "no browser end-to-end tests"); the browser-side typing/offline/reload behaviours are covered by the engine, transport and store unit tests plus the build, not by a browser test. The conflict panel is an inline non-modal `role="dialog"` (no focus trap) — modal semantics and the lightbox belong to 12. The retry scheduler is client-driven only; no server-side job machinery was added.
